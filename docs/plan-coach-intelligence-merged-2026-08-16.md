# 方案：Coach 智慧恢复——Step3 管线修复 + Planner 结构对话（合并版）

> 日期：2026-08-16 | 状态：仅方案（未改代码）| 基线：`v0.5.1-restructured`
> 本文合并两个来源的分析：
> - 产品对 v0.5.1 的四条反馈（不润色直贴 / 确认时机退化 / 语意拼接 / 重复追问失忆）的根因分析
> - `docs/plan-coach-pro-planner-heuristic.md`（下称"Planner 启发式方案"）的结构对话设计
> 结论先行：Planner 启发式方案的诊断（coach 失去结构判断的表现空间）成立但**优先级排反了**——
> 产品实际抱怨的是 Step3 落槽管线的功能性缺陷，必须先修；结构对话作为第二层增强保留。

---

## 1. 合并诊断：两类问题，两个层次

### A 类：Step3 落槽管线的功能缺陷（产品四条反馈的根因，必修）

根因一句话：**秘书架构把"学生原话逐字落槽"当成了真相源原则，顺手把 LLM 在管线入口的三个判断（意图、质量、归属）全部短路了。**

| 产品反馈 | 机制（代码定位） | 本质 |
|---|---|---|
| 不再润色，直接贴进去 | `server.ts:4303` `appendMinute(sp,"student",msg)` 逐字存原文；`secretary.ts:303` 原样上板 | 为防"LLM 代写后走形式确认"，把整理环节整个删了——从"不许代写语义"过度矫正成"不许任何语言加工" |
| 确认时机变了、生硬推流程 | `server.ts:4269-4304`：正则三分类（纯确认/纯拒绝/其余一律实质），**任何实质发言立即 landed**；lens 判 thin/off_target 只产 hint **不拦落槽** | 确认触发从"质量够了"退化成"说话了就算"；文本说"还偏薄"看板却已挂草稿，自相矛盾 |
| 前后句语意拼接 | 整条消息进 firstEmpty 一个槽；v0.2 的批量拆分协议（一条消息拆多条 pendingDrafts 落连续空槽）在新架构无对应通道 | 缺"一条消息覆盖多 beat"的拆分通道 |
| 重复追问 / 记忆错挂 | `我前面已经说过了啊` 被正则判为实质 → **抱怨本身被当内容落槽**；LLM 无任何"从历史回填"通道 | 意图分类只有三类，缺 meta 发言处理与 backfill 动作 |

### B 类：Coach 结构判断的表现空间缺失（Planner 启发式方案的诊断，成立）

- Planner 是静默黑盒，学生看不见"为什么这样分段/哪点详写/让步放哪"；
- Step3 教练被禁止谈结构（`server.ts:8303/8461`），沦为槽位播音员；
- 判断透镜只做内部审计不说给学生；
- Step3 开讲文案只有"我们开始构建这个主体段。"

### 两类问题的关系

A 类决定"教练做没做对"，B 类决定"教练显得专不专业"。**先做对，再显得专业**——
顺序反了会出现"结构讲解得头头是道、学生的话照样逐字上板"的割裂体验。

## 2. 共同设计原则（两方案一致的部分，全部保留）

1. **骨架冻结后只读**：任何环节不得改已冻结结构——消灭死锁的底线，不触碰。
2. **LLM 出判断，代码管状态**：LLM 恢复的是"意图分类 / 质量裁决 / 归属判断 / 结构建议"四类判断权；状态写入（落槽、确认、骨架）仍全部走确定性代码并校验。
3. **不加硬门禁、控制轮次**：所有新增对话 ≤1–3 轮、有默认建议可跳过；门禁只管状态不管对话自然度。
4. **复用现有机制**：提案通道（proposal.ts）、双轨透镜（lens.ts + step3Assessment）、landingLog/replayLanding 都是现成抓手，只扩展不推翻。
5. **反代写红线**：教练不写句子、不加事实；整理/润色只做语言加工，由确定性校验兜底（见 3.1）。

---

## 3. P0：Step3 管线修复（本轮核心，直接对应产品四条反馈）

### 3.1 恢复整理层，加确定性防代写校验（治"不润色直贴"）

- minute 改双字段：`rawText`（学生原话，真相源，进 landingLog/重放）+ `displayText`（LLM 整理稿，看板显示）。
- LLM 在 `step3Assessment` 里附带 `polishedText`，职责**仅限语言加工**：去口水词、理顺语序、补全省略主语——禁止新增论点、事实或学生没说过的语义。
- 服务端确定性校验，不达标回退显示原文：
  - 关键词/实体覆盖：polished 中的名词性实体必须 ⊆ rawText 实体 ∪ 槽位 label 词汇（防加料）；
  - 相似度下限：复用 `secretary.ts` 的 LCS similarity，`similarity(polished, raw) ≥ 0.45`（下限防代写，无上限——整理本来就该变美）；
  - 长度比：`polished.length ≤ raw.length × 2`。
- 落点：`secretary.ts` appendMinute 签名扩展 + `renderBoard` 显示逻辑 + `server.ts:4303` 附近接入校验。

### 3.2 质量门控接回落槽（治"确认时机退化/生硬"）

- `step3Assessment.verdict` 已在双轨产出（`server.ts:4333`），让它参与落槽决策：
  - `ok` → 正常 landed，看板出待确认草稿；
  - `thin` / `off_target` → 本轮只记 `recorded` **不 landed**，看板不出草稿；透镜 hint 照常给教练做追问依据；
  - `duplicate` → 维持现有 dup 预检拒绝路径。
- 效果：文本（"这环还薄，再补一句"）与看板（无草稿）重新一致；确认时机恢复"质量驱动"。
- 护栏：LLM 未输出 assessment 或 slotKey 不匹配时，回退到确定性透镜 `evaluateMinute` 的 verdict，再回退现状（落槽）——拿不准放行，不误杀。

### 3.3 拆分通道（治"语意拼接"）

- LLM 在 assessment 里声明本条消息覆盖的 beat 数与分段（`beats: string[]`，每段对应一个连续空槽）。
- 服务端复用 v0.2 批量协议的确定性校验：必须是**从 firstEmpty 起的连续空前缀**、不跨 pointBlock、≤3 条；校验通过则拆成多条 minute 分别 landed（每条仍过 dup 预检与 3.1 的整理层），不通过则整条落单槽（现状）。
- 学生侧确认形态：看板上多条草稿各自带「确认/改」，一次可全过——v0.2 批量确认的交互体验以确定性形式回归。

### 3.4 意图分类扩容 + 历史回填（治"重复追问/失忆"）

- 意图从三类扩到六类（LLM 判断，非正则）：`content / affirm / reject / meta（抱怨、澄清、"我说过了"）/ question（学生反问）/ correction`。
  - `meta`、`question` **不进落槽管线**，只进对话；
  - 正则三分类降级为 LLM 未输出意图时的兜底。
- 新增 `backfill` 动作：LLM 指出某条历史 minute（或 Step1/2 材料池条目）可填当前槽 → 秘书校验（该 minute 存在、未 confirmed 到其他槽、过 dup 预检）→ landed，等学生确认。
- 学生说"我前面已经说过了啊"时的正确行为：coach 引用历史原话回填并请确认，或明确指出"你说过 X，但缺 Y 这环"——而不是原样重问。
- 配套：stall guard 从"只报警"升级为触发信号——同槽 3 次未确认时，强制 coach 下轮选择 `rephrase / backfill / defer` 之一（defer = 暂挂该槽稍后回填，需秘书支持乱序落槽，landingLog 天然可审计）。

### 3.5 确认动作走 decision 通道（顺手降轮次与成本）

- 看板「确认写板」按钮不再发送字面"对"走完整 LLM 轮次，改走 Step2 已有的 decision 通道（`proposal.ts` 范式）：确定性 commit + 本地推进，零 LLM 调用。
- 文本里的自然语言确认（学生打字说"对"）维持现状走 3.4 的意图分类。

**P0 验收**（对照产品四条反馈逐条回归）：
- [ ] 学生口语化回答上板前经整理层润色；校验回退时显示原文
- [ ] 回答偏薄时看板不出草稿，文本追问与看板状态一致
- [ ] 一条消息覆盖两个 beat 时拆成两条草稿分别落连续槽
- [ ] "我前面已经说过了啊"不落槽；coach 回填历史或指出缺口
- [ ] 确认按钮不触发 LLM 调用；三题型 replay 脚本全绿

## 4. P1：结构透明（保留 Planner 启发式方案的 P1，原样采纳）

纯文本层、低风险，与 P0 并行做：

1. **后置方案确认（post-planner recap）**：Planner 生成后、进 Step3 前，`renderPlanRecap(skeleton)` 纯函数从骨架投影一段大白话方案汇报（"这一篇写两段：第一段展开优势…第二段让步…"），带「照此开始」确认，不新增结构字段。
2. **逐段透明（Step3 kickoff recap）**：每个 body 开讲第一句点明"本段论证什么、为何在这"，替换"我们开始构建这个主体段。"（改 kickoff ContextSummary + 一条 prompt 规则）。

落点与验收同 Planner 启发式方案 §3.2/§3.3、§5-P1。

## 5. P2：Planner 前置结构对话（保留 Planner 启发式方案的核心，降优先级）

原方案 §3.1 全部保留：新增 `layout_strategy` 提案（采纳/拒绝/自定义）、学生选择写入 `plannerPayload.layoutPreference` **软参数**、Planner prompt 加"偏好优先但与材料硬约束冲突时以材料为准"。

调整两点：
- **时机**：必须在 P0 之后上——Step3 管线还是生硬的时候加结构对话，只会放大流程感；
- **轮次预算**：P0-3.5 省下的确认轮次对冲本阶段新增的 1–3 轮，要求净轮次不增（用 §7 的回归集度量）。

## 6. P3：判断进对话 + Prompt 减负

1. **判断进对话**（Planner 启发式方案 §4 保留）：verdict/reason 转成教练 1 句专业点评；偏薄追问带论证逻辑教学；允许教练给专家推荐。
2. **Prompt 减负**（原方案未覆盖，新增）：
   - CTA 结构化：`progressUpdate.cta = { action, target }` 字段替代"进入第二步"字面短语解析，斩断文案硬耦合；
   - 能确定性校验的规则从 prompt 下沉到 guard（P0 完成后，落槽相关 CRITICAL 条款大部分可删）；
   - 用 §7 回归集做删规则的安全网。

---

## 7. 评估闭环（原方案缺失，新增，P0 之前先建）

没有度量手段，所有改动都是盲人摸象（v0.2→v0.3 一行 prompt 实验的教训）。

- 基于 `scripts/replay-*` 系列与 `docs/recorded-sessions/` 真实卡死语料建回归集：至少覆盖 agree-disagree / discussion / problem-solution 三题型各一条完整旅程 + 两个已知卡死场景。
- 量化指标：Step3 完成总轮次、同槽连续追问次数、确认撤销率、stall 触发次数、单会话 LLM 调用数。
- 每期 PR 的门禁：replay 全绿 + 指标不比基线差（净轮次不增、stall 不增）。

## 8. 总排期与风险

| 阶段 | 内容 | 风险 | 前置 |
|---|---|---|---|
| 评估闭环 | replay 回归集 + 指标基线 | 低 | 无，先做 |
| P0 | Step3 管线修复（3.1–3.5） | 中（动落槽入口，但全部有确定性校验 + replay 兜底） | 评估闭环 |
| P1 | 结构透明（recap × 2） | 极低 | 无，可与 P0 并行 |
| P2 | Planner 前置结构对话 | 中 | P0 稳定后 |
| P3 | 判断进对话 + prompt 减负 | 低 | P0（删规则依赖管线稳定） |

**风险边界**：
- 整理层的相似度校验可能误杀合理润色 → 阈值先松后紧，回退行为安全（显示原文），用回归集调参；
- verdict 门控可能因 LLM 误判 thin 导致该落不落 → 双轨回退链（LLM → 透镜 → 放行），拿不准放行；
- 结构对话的流程感反噬 → 保留原方案红线：≤3 轮、可跳过、非硬门禁、净轮次不增。

**两方案关系说明**：本方案不推翻 Planner 启发式方案的任何设计，只是重排优先级（其 P1 → 本 P1，其核心 §3.1 → 本 P2，其 §4 → 本 P3 上半），并补上它缺失的 P0（产品反馈根因修复）与评估闭环。
